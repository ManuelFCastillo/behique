The app under test

Login

A username and password form. The only valid pair is admin / secret123, and it is printed on the page. Messages: "Welcome, admin!", "Invalid credentials", "Username and password are required".

Todo list

Add, tick and delete tasks, with a "N tasks remaining" count. Saved through a JSON API at /api/todos (GET, POST, PATCH, DELETE) into a SQLite database, so a reload shows what was really stored.

Widgets

A colour list, a terms checkbox, size radio buttons, a button that toggles a panel, a "Load data (delayed)" button that takes 1.5 seconds, and a "Show alert" button.

How a bug is counted

  1. One bug is planted. The app is copied and exactly one line of its code is changed. Behique then explores it with no documentation.
  2. Behique reports defects. Each report comes with an assertion: what a correct app would show or return, written as a check the computer can run.
  3. The assertion is replayed twice. It must fail on the buggy app and pass on the clean app. Only then does the bug count as found.

What this baseline does not tell you

  • One bug is out of reach. H3 needs a test-only reset endpoint that a black-box tester cannot see, so it is listed but not scored.
  • The original app has a real bug nobody planted. A single task reads "1 tasks remaining". Both models found it in 9 of 29 runs. It is a true defect, so it is counted as its own category and not as a false alarm, and it never counts toward the planted score.
  • Some reports are guesses. Models sometimes assume an endpoint such as GET /api/todos/1 or /api/login that the app never had, or a field name it does not use. Those are false alarms. Baseten's Spark Open made far more of them.
  • Some bugs cannot be known without a spec. The correct alert text, colour message and error wording are not written anywhere a tester can see. My reading is that this is part of why S10, C8, C9 and H7 were missed by both models, though I have not tested that.
  • One run per bug, per model. A miss may be bad luck and a find may be good luck. Two bugs, C1 and S2, were also used while tuning the explorer, so they are marked "seen in smoke test" and also shown separately above.
  • One Baseten run was repeated. Its first H4 attempt crashed on a screenshot timeout in my harness, not in the model. I raised the timeout and ran that one job again; the second result is the one counted.
  • The clean-app sample is small. Two runs per model is too few to say how often either one raises a false alarm on a correct app.
  • The explorer's instructions are generic QA habits (try valid input, then invalid input; check after a reload; probe the API). None of them mention these specific bugs.
