Behique's senses

Three senses, each with one job, so Behique can test apps that draw everything on a canvas.

Partly built. pixels.mjs and hands.mjs exist and are tested; the other files below do not exist yet. Each card says which part of today's code it grows from. A fourth sense, Guabancex, is planned after the first three and is the first thing cut if time is short. Full plan: docs/canvas-senses-plan.md.

The problem

Behique reads a web page through its accessibility tree: the list of buttons, fields and labels the page declares. That works when the page is made of normal elements. A canvas app such as Music Blocks draws its whole workspace on one element, so the tree shows one blank rectangle and Behique cannot tell what is on it, or click any part of it.

Today a screenshot already goes to the model with every step, but the model can only describe it. It cannot point at anything in it, and the screenshot is not kept as evidence. Actions all need a selector, so there is no mouse position and no drag.

The three senses

Named for three zemís (Taíno spirit figures), in the same spirit as Behique itself. The names are used in headers and in this UI. The files use plain names.

Visual perception

Canvas Vision
File
src/senses/vision.mjs
Built, tested on the test app Model to locate Diff is code
What it does
  • Captures screenshots and finds objects and shapes in them.
  • Produces target coordinates, with a confidence and an honest "not found" when nothing is there.
  • Detects differences between two screenshots with a plain pixel diff, above a measured noise floor.

Action and verification

Márohu

Canvas Interaction
File
src/senses/hands.mjs
Built, tested on the test app No model
What it does
  • Moves the mouse, clicks, drags and presses keys at coordinates.
  • Captures the canvas before and after, and checks whether the action worked: pixels changed in the expected place, a request fired, nothing broke.
  • Replays the same action in a fresh browser, so a finding can be proven again.

The selector-only act(), src/session.mjs. Coordinate actions are new and are not offered to the explorer until they work.

Performance

Guabancex

Performance Tester
File (planned)
src/senses/performance.mjs
Planned, after Phase 2 No model
What it does
  • Measures page load time, long tasks, JavaScript memory growth, requests and bytes transferred, and frame rate during a scripted action.
  • Repeats each measurement on each version, finds how much the same version differs from itself, and reports a slowdown only when it is bigger than that.
  • Matters most for canvas and WebGL apps, where frame rate can drop between releases and neither the accessibility tree nor a screenshot shows it.
Grows from today's code

The build runner and version-against-version pipeline in src/release/. Playwright and the Chrome DevTools performance metrics supply the numbers; nothing in it is new infrastructure.

What it may claim

Statistical findings, written by code, with the noise floor shown next to them.

Cautions

Numbers only mean something version against version on the same machine. Headless Chromium draws in software unless GPU flags are set. Music Blocks slows itself to 1 frame per second when idle, so frame rate has to be sampled while something is running.

How they work together

LookMacocael reads the tree. Boinayel reads the pixels.
→
ProposeA target: where to click, with a confidence and the reason.
→
Act and checkMárohu clicks, captures the result and gives a verdict.
→
RecordEvidence goes to the tamper-evident record. A person decides Ship or Hold.

The rules

  1. Perception proposes, the runtime verifies. A vision model can say a button is at a place. Only a deterministic check can certify anything: the click changed these pixels, fired this request, or did nothing.
  2. Assertions are data. New kinds of check are fields the runtime evaluates, never code written by a model.
  3. "Not found" is a real answer. Boinayel may return nothing. It must never invent a target to look useful.
  4. Confidence comes from verification. A model's own confidence number is not calibrated. A target is trusted when Márohu's click changes the state as predicted, and a click that changes nothing is low confidence whatever the model said.
  5. Measure the noise first. Run the same version twice and record how many pixels differ by themselves. Only report differences between versions that are above that floor.

Which model sees

Muse Spark 1.3 is enough. Measured on 139 calls: with the right settings it points at objects to within about one pixel. No Fireworks or Modal is needed to find things on a canvas.

  • Coordinates as 0 to 1 decimals. 98.9% hits, median error 0.8 px. Plain pixels hit 91.7% and 0 to 1000 had a heavy tail of bad calls.
  • Screenshots at device scale 2, reasoning low. Larger images were stable; small ones sometimes came back with one error shared by every object. Low reasoning halves the cost with no loss.
  • Never a tall full-page screenshot. Beyond about 2,000 px tall it failed in every format, so the visual senses use viewport-sized shots.
  • It says "not found" when something is not there. 0 invented objects in 59 queries.
  • Its own confidence is not trustworthy. Answers more than 50 px off had higher confidence than correct ones. That is why Márohu verifies every target by clicking.
  • Real app too. On Music Blocks (v3.8.0) it found all toolbar icons and 7 of 7 real canvas blocks, with positions from the app's own model as truth.

Still open: data retention and training use, rate limits and the stated image size limit. Until answered, only public apps are sent to the model. The Fireworks and Modal credits are not confirmed claimed, and are not needed.

What is proven so far

True today The accessibility tree, screenshots, network and console are read on every step. A finding only counts if its replay fails on a fresh copy of the app.

Measured A model can point at canvas objects accurately and says "not found" honestly (Phase 0). On Music Blocks, canvas blocks are invisible to the accessibility tree in v3.8.0 but listed by name, without positions, on the current master: the semantic sense says what is there and the visual sense says where.

Measured On the test app, a click at a known position changes the expected pixels, a click on empty canvas changes none, and the same click gives the same verdict in 3 of 3 fresh browsers (Phase 1).

Measured With the model proposing controls and the pixels deciding, 18 of 18 planted bugs on the test app were found and replayed 3 of 3 on both models, with nothing flagged on the clean app (Phase 2). A bug that only changes a word on screen was not found: pixels cannot tell a wrong word from a right one.

Measured On Music Blocks the same click twice in fresh pages gave the same screen for 26 of 31 and 31 of 33 controls, and the version difference was readable: 6 toolbar controls moved, 1 new control on master, the canvas blocks unchanged. The dead-control rule has no power there, because almost every click changes the screen.

Built Findings are written into the evidence store: the model's proposal as a guess it cannot make a verdict from, the result as a reproduced failure written by code, with before, after and diff pictures, shown on the report page (tagged canvas).

Not proven That the senses can find a real bug in a real app (none was planted in Music Blocks), and that they can run inside the explorer on their own. The test app is easy and the click-radius rule was tuned on it.
