Behique's senses

Three senses, each with one job, so Behique can test apps that draw everything on a canvas.

Plan, not built. The three files below do not exist yet. Each card says which part of today's code it grows from. Full plan: docs/canvas-senses-plan.md.

The problem

Behique reads a web page through its accessibility tree: the list of buttons, fields and labels the page declares. That works when the page is made of normal elements. A canvas app such as Music Blocks draws its whole workspace on one element, so the tree shows one blank rectangle and Behique cannot tell what is on it, or click any part of it.

Today a screenshot already goes to the model with every step, but the model can only describe it. It cannot point at anything in it, and the screenshot is not kept as evidence. Actions all need a selector, so there is no mouse position and no drag.

The three senses

Named for three zemís (Taíno spirit figures), in the same spirit as Behique itself. The names are used in headers and in this UI. The files use plain names.

What it does
  • Moves the mouse, clicks, drags and presses keys at coordinates.

The rules

  1. Perception proposes, the runtime verifies. A vision model can say a button is at a place. Only a deterministic check can certify anything: the click changed these pixels, fired this request, or did nothing.
  2. Assertions are data. New kinds of check are fields the runtime evaluates, never code written by a model.
  3. "Not found" is a real answer. Boinayel may return nothing. It must never invent a target to look useful.
  4. Confidence comes from verification. A model's own confidence number is not calibrated. A target is trusted when Márohu's click changes the state as predicted, and a click that changes nothing is low confidence whatever the model said.
  5. Measure the noise first. Run the same version twice and record how many pixels differ by themselves. Only report differences between versions that are above that floor.

Which model sees

Measure first, then choose. Muse Spark 1.3 is already wired and fits a Meta hackathon, so it goes first. If it cannot point well enough, Fireworks is the fallback (a vision model with grounding, a few lines to add). Modal is only for a real detector with calibrated scores, which is probably not worth it before the deadline.

Nothing is known yet about how Muse Spark handles images: Muse Code answered "unknown" for every spec. Data retention, rate limits and the image size limit are still open. Until they are answered, only the public test app is sent to any model. The Fireworks and Modal credits are not confirmed claimed.

What is proven so far

True today The accessibility tree, screenshots, network and console are read on every step. A finding only counts if its replay fails on a fresh copy of the app.

Not proven That any model can point at canvas objects, that a click can be replayed reliably across versions, and that pixel differences stay above the noise. Phase 0 and 1 answer these.
