1. What Behique is

An autonomous release-verification and visual QA tool. You give it a known-good release and a release candidate of a web app. It records what each one shows along real click paths, finds what changed, replays every change on a fresh build to prove it is real (3 of 3 on each side), finds the exact commit that caused it, and writes an evidence-backed report. A model proposes, code verifies, a person approves. A bug only counts when a replayable assertion proves it, and the Ship or Hold decision is always a person's.

3. The result that matters

With no hand-written steps, the crawler plus compare reproduced the FreshRSS Share regression: the share button's data-url and data-title are now URL-encoded. The crawl visited 30 states and produced 37 steps. The two changes were confirmed 3 of 3 on the good build and 3 of 3 on the candidate. Bisect found commit 1b7178a in 8 steps, the same commit the hand-written case gives. The same comparison started from the dashboard returned HOLD with 2 reproduced changes and a screenshot.

Read this as: the mechanism works. It is not evidence that it works on any app, because FreshRSS is the app the crawler was tuned on. The first runs of the crawl returned fails_both because recorded steps shared state across flows. The fix (replay each flow alone, read-only, cookies and storage cleared between flows) is what made it honest.

5. Safety: what was blocked and why

Twice the six-repo run was refused by the permission policy on the Mac: it does not allow installing dependencies and starting dev servers from freshly cloned third-party repos unattended, because that runs the repo's code on your Mac. I did not work around it. That is why Phase 4 was built: the same runs, executed in Docker on hardac2, were accepted, and nothing from those repos ran on the Mac.

  • Behique's own safeguards: installs run with scripts disabled; commands come from an allowlist; clone and set-up run only with the fingerprint of what a person reviewed; the crawler sends only GET and aborts cross-origin requests.
  • I read each proposed command list before running it. Everything still runs only when BEHIQUE_SANDBOX is set; without it, profile apps run as normal host processes, as before. A mistyped value is an error, never a silent fallback to the host.

6. Phase 4: untrusted repos run in Docker, with database sidecars

Decision: one Docker runner with two targets, switched by BEHIQUE_SANDBOX. hardac2 over ssh is the real target (x86_64, Docker 29.9.2, 24 cores, KVM available); OrbStack on the Mac is the local option (arm64, daemon was off, not used today). Full details: docs/sandbox.md.

How it works

  • Each check gets an internal network (no outside access) and an open one. Sidecars (Postgres, MySQL, MariaDB, Redis, MongoDB) and the app run on the internal one; install steps also join the open one for the package registry.
  • The app is reached by its container address through a tunnel, so everything else in Behique still sees http://127.0.0.1:port. Nothing is published to hardac2's network.
  • Every container: all capabilities dropped, no-new-privileges, read-only root, non-root user (databases excepted, with a minimal capability set), memory, CPU and process limits, deleted after the check. Lifecycle scripts stay disabled on installs.
  • Every docker argument is built by code from validated parts (docker-args.mjs); nothing from a repo, a model or a page can become a docker flag. This matters because the docker group is root-equivalent on hardac2.

Bugs the real runs found (all fixed, each with a test)

  • Docker copies the image folder's owner (root) onto a still-empty volume at first mount, silently undoing the permission fix. Fixed with nocopy.
  • /tmp must allow execution: yarn Berry writes launchers there. Yarn Berry also refuses --ignore-scripts; scripts are now turned off the way each yarn version accepts.
  • Dev servers that listen only on localhost were unreachable from outside the container. A small launcher inside the container relays to them.
  • The default Node image lacked openssl (Prisma needs it); next build was killed at 4 GB (needs about 10 GB); the model's run start -- -p {port} breaks with pnpm and yarn Berry.
  • An ssh tunnel through the shared connection exited at once; it now uses its own connection.

Limits: plain Docker (runc) is not a hard wall; before arbitrary repos, move to Firecracker or gVisor. The sidecar proposer missed umami's Postgres (its compose file names a service db with no hint). The repair loop now ran for real (see above) under a narrow standing approval; anything outside it (a new program, npx or dlx, scripts on) stops for a person. Phase 3 (seed data) is not built.

What it took

  • The first full run gave 1 confirmed, 1 no change, 4 failed. Three failed because the good version compared with itself still differed (a rotating testimonial, a locale that flipped at one step, a dialog open in one recording). One was an install that hit the 15-minute limit.
  • Fix: facts the control disagrees on now join the noise mask (an element noisy at three or more steps is masked at every step), and a fresh control must come back clean, up to 5 extra recordings. Cost: a real change inside a masked fact cannot be seen. This needs a second look.
  • Also fixed: a 3 s navigation limit that left excalidraw with 0 pages (now 30 s, and the reason is logged); a crawl with nothing to click now loads /; text findings compare the element's own text exactly (own_text) because a substring check made text changes unconfirmable; a stalled-install watchdog (8 minutes without output, one retry on a fresh container, not yet seen to trigger on a real repo).
  • Run times were 1 to 38 minutes per repo, mostly installs and builds.

Planted changes

bench/planted-bench.mjs (a small generated app, 9 single changes plus a comment-only change): 8 of 8 visible changes found, 7 of 8 confirmed as a test, 0 false positives on the comment-only change. The one found but not provable is an added disabled attribute (an added fact has no value to assert against); a background-colour change is left to the picture check.

Known weak spots

  • The crawler was tuned on one app and has now run on six more, once each, with thin or degenerate coverage on three of them (excalidraw, umami, html5-boilerplate). No login or seeded data, so apps behind a login are out of reach.
  • The repair and check results are one run per repo on six public repos we picked; not repeated, not a success rate.
  • Noise learning hides facts (nextjs-blog 1,223, todomvc 66, vitepress 40); a real change inside them would be missed.
  • ~/dev/behique-ui/behique-live.html (the dashboard page) is not under git; backups exist only in a scratch folder.
  • A Ship or Hold decision's name is typed in, so it is attribution by honour, not identity.
  • The demo script was updated on 2026-10-30 (new beat 10 shows the six-repo results as saved runs, not live); the live beats still use hand-written FreshRSS steps.
