## Run 1: VitePress #2949

Answer key (written 2026-11-01 before the run): culprit 070fc0a5 "feat(theme): use inert to avoid traverse menus and content with keyboard (#2932)", inside v1.0.0-rc.10..v1.0.0-rc.12 (25 commits). The fix in rc.13 is a revert of that commit. Symptom: on a production build, a doc page loaded directly has `inert` on `aside.VPSidebar`; clicking its links does nothing. Commenters say the dev server does not show it, so the profile `vitepress-docs` serves the production build with `vitepress preview`.

Risk noted before the run: the crawler starts at `/` and reaches doc pages by clicking, which is client-side navigation. If the record never loads a doc page directly, the check may not see the attribute. That is a limit of the crawl, and it is a fair result if so.

### Run 1a (2026-11-01 20:28 UTC, case `20261101T202836Z_v1.0.0-rc.10-vs-v1.0.0-rc.12`): a miss, and a useful one

- Verdict HOLD, 2 of 2 findings confirmed 3/3 and 3/3, 25 commits bisected in 5 steps, parent verified, chain verified. Total 617 s with a warm cache.
- **Found it: no.** The findings were R1, the version label in the nav bar (`1.0.0-rc.10` to `1.0.0-rc.12`, ranked "a person would notice", text a person reads) and R2, a scoped-style `data-v-` attribute that moved (markup churn). The word `inert` appears nowhere in the record.
- **Named the commit: no.** The bisect followed R1 and landed on d55ce0b "release: v1.0.0-rc.11", the commit that bumps the version in `package.json`. Correct for the question it asked, wrong for the regression.
- **Explained it:** not asked; there was no culprit to explain.

Why, read from the record rather than guessed: the crawl's 4 flows all start at `/` and reach the doc pages by clicking, which is client-side navigation; no step ever loaded a doc page by address, which is exactly where the issue says the bug shows. And had it loaded one, `inert` would have arrived as an *added* attribute, and added facts never became tests. Three changes to the pipeline followed, each with unit tests:

1. The crawl adds a direct load of every page its clicks reached (up to 8), as its own flow; a `goto` of another page is a flow boundary and the first replayed action of its test (`crawl/plan.mjs`, `findings.mjs`, `confirm.mjs`, `facts.mjs`).
2. A state attribute newly set on an element both versions have (`inert`, `disabled`, `hidden`, `readonly`, `aria-*`) becomes a finding whose test expects the attribute absent; new op `absent` in the assertion runtime and the exporter (`findings.mjs` `appearedStates`, `assert.mjs`, `export.mjs`).
3. A text that is the release's own version (the good value contains the good ref's version, the candidate value the candidate's, nothing else differs) is classed as churn, so it ranks last and never drives the bisect (`notice.mjs` `releaseLabel`, refs passed from `confirm.mjs`).

The record of run 1a stays as it is. Run 1b below is the same pair on the fixed pipeline, with a fresh crawl.

### Run 1b (2026-11-01 20:51 UTC, case `20261101T205128Z_v1.0.0-rc.10-vs-v1.0.0-rc.12`): still a miss, one gap closer

- Fresh crawl: 5 page states, 7 flows (4 by click, 3 direct loads of `/guide/what-is-vitepress`, `/reference/site-config`, `/guide/getting-started`), 10 steps. 6853 facts recorded, 0.8% masked. Total 362 s, every build cached.
- The version label is now classed "the release's own version label" and the recommendation turned to SHIP with the churn note, which is right for what was proven and wrong for the release: **found it: no.** `inert` is still absent from the record, even on the direct loads.
- Cause, read from the recorder this time: `facts.mjs` keeps a fixed list of attributes, and `inert` was not on it (nor `hidden`, `readonly`, `open`, `aria-disabled` and most other aria states). An attribute that is never recorded cannot be added, changed or missing. The list now includes those states.
- Also visible in this run: the bisect follows the first confirmed finding even when it is churn, so it bisected the version label to the release commit again. Harmless with a SHIP recommendation, but a wasted 164 s; when every finding is churn the search could be skipped.

### Run 1c (2026-11-01 20:58 UTC, case `20261101T205838Z_v1.0.0-rc.10-vs-v1.0.0-rc.12`): found it, bisect inconclusive

- 6857 facts, 0.5% masked. Three state attributes newly set on rc.12, all of them `inert` on `body/div[1]/div[1]/aside[1]` (the sidebar), at the three direct-load steps. **Found it: yes.** R1 is that attribute, ranked "a person would notice (a state a person sees (inert))", test passed 3/3 on rc.10 and failed 3/3 on rc.12. R2 is the version label (churn), R3 the scoped-style attribute (churn). HOLD.
- **Named the commit: no, inconclusive.** The bisect tested #12 good, #18 good, then every commit from #19 (070fc0a, the culprit) to #24 came back "skip (Error: expect(received).toBeNull())" and the search ended with "the first bad change is one of 7 (#19 to #25)". The search had the right answer in hand and could not read it: `bisect.mjs` `classify` only counted `toBe(`, `toContain(` and `toMatch(` failures as "bad" and treated anything else as a skip, so the new `toBeNull()` failure of the absent-attribute test was filed under "could not be tested". Fixed with a test: any failed value assertion (`toBe*`, `not.toBeNull`, `toContain`, `toMatch`) is bad; locator timeouts, build failures and crashes stay skips.
- Total 641 s, bisect 409 s of it (8 builds, 2 cached).

### Run 1d (2026-11-01 21:10 UTC, case `20261101T211047Z_v1.0.0-rc.10-vs-v1.0.0-rc.12`): found it and named the commit

- Same crawl (7 flows, 10 steps), 6876 facts, 0.8% masked, control 0 differences. Three findings, all confirmed 3/3 and 3/3: R1 `inert` newly set on the sidebar `aside` at a direct load (a person would notice), R2 the version label (churn), R3 a scoped-style attribute (churn). HOLD.
- **Found it: yes.** R1 is the symptom in the issue: the sidebar carries `inert` after a direct load of a doc page.
- **Named the commit: yes.** Bisect #12 good, #18 good, #21 bad, #19 bad: first bad change is #19 of 25, [070fc0a](https://github.com/vuejs/vitepress/commit/070fc0a56ddb941e26a098ba7207b5d1e91b7b51) "feat(theme): use inert to avoid traverse menus and content with keyboard (#2932)", 4 steps, parent c0ce7f7 verified good 3/3, 070fc0a verified bad 3/3. That is the commit the project reverted in rc.13. The run never saw the issue, the revert or any commit after rc.12.
- **Explained it:** not yet asked. The Ask-why call is the person's to send from the dashboard (one call, about a cent).
- Total 401 s with every build cached (compare 120 s, tests 92 s, pictures 36 s, bisect 152 s).

What this run cost to get right, in order: the crawl had to load pages directly (1a), the recorder had to record state attributes (1b), an attribute that appears had to become a test (1a), and the bisect had to read that test's failure (1c). None of these was specific to VitePress; each is a class of bug the pipeline could not see before today. The four cases stay in `out/evidence/` as the record of the sequence.

## Run 2: Hoppscotch #5693

Answer key (in the table above, written 2026-11-01 before the run): culprit d67a85b "fix(common): remove double scrollbar in response pane (#5665)", inside 2025.10.1..2025.11.2 (41 commits); the fix is PR #5695 in 2025.12.0. Symptom: the `/settings` page cannot scroll because `<main>` lost its `overflow-auto` class. The repo was cloned with no profile, so the dashboard's set-up flow is the first graded step.

### Set-up from zero (2026-11-02 05:34 UTC, from the dashboard)

- Settings first: sandbox set to Docker over ssh on hardac2 (the test button answered "Docker 29.9.2 is reachable"). Set up an app: repository `hoppscotch`, name `hoppscotch`, 2025.10.1 against 2025.11.2. The review showed the exact text (22.6 KB) and the cost; the proposal came back in 12 s for $0.0152 (muse-spark-1.3): `pnpm install`, `pnpm run generate`, serve `npx http-server packages/hoppscotch-selfhost-web/dist`. That mirrors the repository's README.
- **First verification failed in 24 s**: "Step 2 (pnpm run) exited with code 1", and that one line is all the dashboard showed. The log exists (the check keeps the last 4000 characters) but the set-up state drops it, so it had to be fetched by re-running `verifyProfile` from a script. It said: js-sandbox could not resolve `@hoppscotch/data`. Cause: Behique installs with `--ignore-scripts` (by design), and Hoppscotch does its real build work in lifecycle hooks: `prepare` builds the workspace libraries (data, kernel, codemirror-lang-graphql, js-sandbox) and `postinstall` generates the backend GraphQL schema (`gql-gen/`, gitignored) and the typed client code in common and selfhost-web. None of that is committed, so `pnpm -r do-build-prod` had nothing to resolve. A proposal that follows the README cannot know this; the Dockerfile shows it.
- **Repair, by hand**: the dashboard has no edit box and the propose-verify-repair loop (`repair.mjs`) is not wired into it, so `out/onboard/hoppscotch.proposed.json` was edited directly and "Verify and save" pressed again. The profile now has 10 install steps in dependency order (install; build data, kernel, codemirror-lang-graphql, js-sandbox; `prisma generate` and `generate-gql-sdl` in the backend; `gql-codegen` in common and selfhost-web; build selfhost-web), serves with `vite preview` so client-side routes such as `/settings` load directly, and carries the `VITE_*` values from `.env.example` plus a placeholder `DATABASE_URL` for `prisma generate`. Two more things got in the way: rollup's `-c` (its config flag) is refused as pnpm's `-c` inline-code flag, so the package's own `prepare` script is run instead; and the selfhost-web build runs node with an 8 GB heap while the sandbox's default limit is 4 GB, so Settings got 12288 MB and 8 CPUs.
- **Second verification passed** (459 s): both builds in about 210 s, pictures settle in 6 s, emptiness 0.971, no page errors, no blocked requests, noise floor 0 pixels. Profile saved as `src/release/onboard/profiles/hoppscotch.json`.
- Graded: the model's proposal was wrong for this repo in a way it could not have known from the facts it was given (it saw the scripts, not the hooks' side effects); the dashboard let a person recover only by leaving it. Three gaps to close: show the failing step's log in the set-up card, wire the repair loop (or at least an edit box) into the flow, and either raise the default memory or read `--max_old_space_size` from the build script.

### Run 2a (2026-11-02 05:53 UTC, case `20261102T055326Z_2025.10.1-vs-2025.11.2`): named the commit, missed the symptom, and recommends SHIP

- Crawl of 2025.10.1: 7 page states, 9 flows, 14 steps, stopped by the 122 s budget; it reached `/graphql`, `/realtime/websocket` and `/settings` by clicking, and 11 planned flows failed at their second step. 6461 facts, 10.1% masked (638 of them under `body/div[1]/div[1]`), control recording 0 differences. Candidate: 893 differences (added 452, removed 421, moved 20, changed 0).
- Findings R1 and R2: the scoped-style attribute `data-v-f947af81`, present on the good version at two layout roots and missing on the candidate. Both classed markup churn, both confirmed 3/3 and 3/3. Recommendation **SHIP** with the churn note.
- **Found it: no.** `class` is not in the recorder's attribute list (`facts.mjs` `ATTRS`), so the whole culprit diff (`!overflow-auto` to `!overflow-hidden` on three `Pane` elements in `PaneLayout.vue` and `default.vue`, 5 lines) is invisible to the check. The scroll-position fact could not show it either: no crawled step scrolls, and `/settings` at 1280x800 was recorded at the top.
- **Named the commit: yes, for the wrong reason.** Bisect in 5 steps (#20, #30, #35, #38 good, #39 bad): [d67a85b](https://github.com/hoppscotch/hoppscotch/commit/d67a85b1287e8224b0f72a931b96fec184ebf9b9), parent e51676e verified good 3/3, culprit verified bad 3/3. That is the answer key. But the test that drove the search was the `data-v` attribute: the culprit edits the scoped styles of the two layout components, so Vue's style hash moved in the same commit. The search followed the churn and landed on the right commit because the churn and the bug share a commit. Had a neighbouring commit touched those styles, it would have named that one with the same confidence.
- **Explained it:** not asked.
- Timing: total 1281 s; bisect 1153 s (11 builds, 6 cached, 5 fresh at about 3.5 min each), compare 88 s, tests 30 s, pictures 10 s. Evidence log verified.
- What the record asks for, not built yet: class lists as facts (a stable attribute on most apps, but a rule is needed for which class changes a person would notice: `overflow-*`, `hidden`, `invisible`, `opacity-0` are plausible, generated names are not), and a scroll probe per recorded page (can the scrolling element scroll, and did the page scroll when asked to) so that "cannot scroll" becomes a difference. One cosmetic thing: with a SHIP recommendation the bisect timeline still labels the candidate end "bad".

### Run 2b (2026-11-02 17:29 UTC, case `20261102T172913Z_2025.10.1-vs-2025.11.2`): found it and named the commit

Between 2a and 2b the recorder gained two facts (`docs/STATUS.md`, "Class facts and a scroll probe"): the element's class list, sorted, and `#scrolls`, set on any element whose content is taller than its box with overflow auto or scroll. A class change is "a person would notice" only when a class that shows, hides or scrolls comes or goes; a lost `#scrolls` becomes a test that asks the same element whether it still scrolls. Both were checked in a real browser before the run.

- Fresh crawl of 2025.10.1: 8 page states, 9 flows, 14 steps, 110 s; it reached `/graphql`, `/realtime/websocket` and `/settings` by click and loaded `/settings` directly as step 14. 14580 facts (twice run 2a's count: class lists are many), 9.9% masked, control 0 differences. Candidate: 1199 differences (changed 83, all of them class lists; added 465, removed 615, moved 36).
- **Found it: yes.** All five findings are the culprit's own change, `!overflow-auto` to `!overflow-hidden` on `splitpanes__pane` elements (R1 the top pane at `start`, R2 to R5 nested panes), each confirmed 3/3 and 3/3. And the scroll probe recorded the symptom as the issue states it: `#scrolls` on the inner pane under `main` vanished on the candidate at step 9 (the click into Settings) and at step 14 (the direct load of `/settings`). Those two did not become tests only because the cap of 5 findings was already full of class changes ranked the same; they are in the recorded diff.
- **Named the commit: yes, for the right reason.** Bisect in 5 steps (#20, #30, #35, #38 good, #39 bad) to [d67a85b](https://github.com/hoppscotch/hoppscotch/commit/d67a85b1287e8224b0f72a931b96fec184ebf9b9), parent e51676e verified good 3/3, culprit verified bad 3/3. The test it followed (R1) checks the class list of the pane, which is the line the culprit changed and the fix in #5695 changed back.
- **Explained it:** not asked.
- Recommendation **HOLD** (5 a person would notice, 0 churn). Total 163 s with every build cached from run 2a (compare 62 s, tests 47 s for 30 runs, bisect 50 s, pictures 6 s). Evidence log verified.
- Left open: five findings for one change (the same class change on five panes) read as five regressions; grouping identical class changes across elements into one finding would leave room under the cap for the `#scrolls` loss, which is the better test of the symptom. An area that newly scrolls is still not tested, and the page's own scrolling element is not probed.

What run 2 cost to get right, in order: the set-up had to be repaired by hand outside the dashboard (lifecycle hooks, memory, a flag rule), then the recorder had to record class lists and whether an area can scroll. The pipeline change is general: any app that hides, shows or locks an area with a class is now visible to the check.

### Run 2c: recordings, one finding per class change, scroll tests that scroll (2026-11-02)

Graded: symptom seen (the overflow class, 3 of 3), commit named, no model call.
